## 1. 研究の目的と背景

- **目的:** 日本人英語学習者のスピーキングに見られる L1（日本語）干渉と化石化（fossilization）を、
  音声認識と LLM を組み合わせて自動で検知し、数値にする。
- **5月時点の構想（研究の肝として挙げていたもの）:** 定期的に課題を解いてもらい、毎回フィードバックを返すことで
  **ミスそのものが減っていくか**を検証する。検証期間、課題の数、課題の種類（英訳／穴埋め／自由発話）は未定だった。
  → 2026-10 時点で未実施。採点のぶれの検証を優先するため、範囲外（今後の課題）とする想定（§6 参照）。
- **評価理論:** 必須文脈（obligatory contexts）。分母を「その文法規則を適用すべき場面の総数」、
  分子を「実際に誤った数」としてエラー率を出す。文単位の正答率と違い、発話量や流暢さに左右されにくい。
  （Brown 1973 の SOC: suppliance in obligatory contexts の考え方）
- **評価する4観点:** 時制／主語と動詞の一致／名詞の境界（単複・冠詞）／構文・語順

## 3. 現行システムの仕様（リポジトリ準拠）

- **構成:** Streamlit（`app.py`、`pages/dashboard.py`、`pages/admin.py`）、OpenAI の Whisper-1（音声認識）と GPT-4o（解析、`temperature=0`）、
  Google Cloud Storage（音声）、Google スプレッドシート `English_AI_Logs`（ログ。テスター情報は `Testers` タブ）
- **処理の流れ（1問ごと）:** 録音またはファイルアップロード → Whisper（`language="en"`）→ GPT-4o で音声認識ノイズだけを補正（cleaned）
  → GCS に音声を保存 → スプレッドシートに `[日時, ID, 問題番号, 問題文, raw, cleaned]` を記録
- **総合診断（10問終了後）:**
  1. 10問分の **raw** テキストをまとめて GPT-4o に渡し、JSON モードで出力させる
  2. 観点ごとに `obligatory_contexts_list`（規則を適用すべき箇所すべて。正しく使えた箇所も含む）と
     `error_list`（そのうち誤った箇所）を、**リストとして**書き出させる。件数は書かせない
  3. 言い直し（self-repair）、単なる言い淀みや繰り返し、音声認識のノイズは、必須文脈にもエラーにも数えない
  4. 件数は Python がリストの長さから数える。エラー率と化石化の判定も Python で計算する
  5. スプレッドシートに `[日時, ID, "FINAL", "総合診断レポート", "", 結果JSON]` を記録
- **全体平均エラー率（診断画面）:** 全観点の誤りの合計 ÷ 全観点の必須文脈の合計（文脈数で重み付け）
- **現行の化石化の定義:** 観点のエラー率 ≥ 全体平均エラー率 + 15ポイント（`app.py:359`）
- **ダッシュボードの CEFR 推定:** 平均エラー率と化石化検知回数から、独自のしきい値で A1〜C2 を割り当てている（`pages/admin.py:76`）

## 4. 化石化の定義の変遷

| 版 | 時期 | 定義 | 備考 |
|---|---|---|---|
| v0 | 5月〜6月上旬 | GPT-4o がプロンプトに従って直接判定 | 計算ミスや判定のぶれが出たため廃止 |
| v1 | 6月報告 | 観点のエラー率が **20%以上**（絶対的基準）**かつ** 全体平均の **1.3倍以上**（相対的基準） | Gemini 版で実装。6月報告ではこれと人手検証の2段階（ハイブリッド型）として提案 |
| v2 | 2026-06-22 | 全体平均が40%以下 **かつ** 観点のエラー率が全体平均＋30ポイント以上 | 移植時の一時的な版（コミット 5005de0） |
| v3（現行） | 2026-06-22〜 | 観点のエラー率が全体平均＋15ポイント以上（絶対的基準は撤廃） | 7月に4名で実験したときの定義。4名中3名で化石化を検知 |

**執筆時の注意:** 方法の章では最終的な定義を1つに決め、その理由を書く。全データをその定義で計算し直す。
加えて、しきい値を何通りか変えたときに判定が変わるかを感度分析として示すと、説得力が増す。
ログに保存された JSON にはリスト・件数・エラー率が入っているので、どの定義でも後から計算し直せる。

## 5. これまでに得られた知見（結果・考察の材料）

### 音声認識（Whisper）
- 1回答あたりの文字起こしミスは0〜2語程度で、実用レベル。発音があやしい部分でもかなり正確に拾う（6月）。
- 文脈に合わない単語に置き換わることがある（club → crab、prefer → play for）。固有名詞の精度は低い（6月・7月）。
- 言語を自動判定させると、日本語や韓国語として文字起こしされる不具合が出た → 英語に固定して解決（7月）。
- 言い直しが文字起こしに残る場合と、残らない場合の両方がある（6月）。

### LLM による採点
- **言い直しによる偽陽性:** 「構文・語順」のエラー率が突出して高く出る傾向があった。生音声を確認すると、
  GPT-4o が言い直しを構造の破綻として過剰に検知していた（6月）。
  SLA 的には、言い直しは自己モニター機能が働いている証拠であり、化石化とは区別すべき現象。
- **計算をすべて LLM に任せたときのずれ:** 手で採点した結果と数値がずれていた → 件数の計算を Python に移した（7月）。
- **cleaned 版の問題:** 指示に反して、文法の誤りや単複の誤りまで直してしまい、誤りが消えた → 分析は raw 版に戻した（7月）。
- **極端な値:** cleaned 版では 0% や 100% が多発した。raw 版で採点し直すと極端な値は減り、目で数えたミスの量とおおむね一致した。
  ただし、理由の分からない 100% が一部に残った（7月）。必須文脈が少ない観点ほど、1件の誤りでエラー率が大きく動く。
- **再現性:** 同じデータを何度か採点すると、毎回結果がずれることが多かった（7月）。
- **人による発話量の差:** 同じ問いでも人によって発話の長さが大きく違い、データとして均一ではない（7月）。

### 課題の種類
- 英訳課題より、認知的負荷が高い自由発話課題の方が、L1 干渉や化石化を検知しやすい（6月）。
  → 分析は自由発話を中心に進める方針。

## 6. 執筆までに決める・実施すること（未確定事項）

進捗報告で「今後」と書いたものと、コードを確認して見つかった課題。

1. **フィードバックによってミスが減るかの縦断検証**（5月の構想）: 範囲外（今後の課題）とする想定。先生に確認する。
2. **全40問の人手採点と、AI 採点との差の整理**（6月の予定）: 結果の章の中心になる妥当性検証。
   人手と AI の一致度は、件数の相関、一致率、Cohen's κ などで示す。
3. **再現性の検証**（7月の課題）: **← 本研究の中心。** `stability_experiment.md` と `experiments/stability.py` を参照。
4. **GPT-4o と Gemini の比較**（7月の予定、**追加研究**の扱い）: どちらが採点プロンプトに忠実で、結果が安定しているか。
   別リポジトリ `automatic-bassoon-gemini` がある。
5. **化石化のしきい値の最終決定**（§4）
6. **英訳課題と自由発話課題を分けて集計するか:** 現在のコードは10問をまとめて分析している。
7. **セット名がスプレッドシートに記録されていない:** セット別の集計には、GCS のファイル名やタイムスタンプから対応付けし直す必要がある。
8. **「平均エラー率」の定義が画面によって違う:** 診断画面は文脈数で重み付けした値、ダッシュボードは観点ごとのエラー率の単純平均。論文中ではどちらか一方に統一する。
9. **CEFR 推定の扱い:** CEFR は文法のエラー率で定義された基準ではない。独自に設けた目安と明記するか、論文からは外す。
10. **`reprocess.py` が新しい形式のファイル名を拾えない不具合:** 検索条件が `prefix=f"{user_id}_Q"` のため、セット名入りの新しい形式が対象から漏れる。
