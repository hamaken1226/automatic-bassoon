# 再実験計画: 採点のぶれを抑えるには

作成: 2026-10-06

## 0. 位置づけ

- 先生の指示: 「今のデータで採点すると毎回結果がぶれる。それを安定させるにはどうすればよいかを、何回か再実験して結論とする」
- **研究の中心:** LLM（GPT-4o）による必須文脈の採点の**再現性（信頼性）**と、それを高める方法。
- GPT-4o と Gemini の比較は、余裕があればやる追加研究とする。
- 5月に構想していた「フィードバックでミスが減るかの縦断検証」は**実施しない（確定）**。論文では今後の課題で触れる。

## 1. リサーチクエスチョン（案）

- **RQ1:** 現行の採点方式では、同じ発話データを繰り返し採点したときに、エラー率と化石化の判定がどの程度ぶれるか。
- **RQ2:** プロンプトと出力形式をどう設計すれば、ぶれを抑えられるか。
- **RQ3:** 書き起こしの誤り（Whisper と手動文字起こしの差）は、採点結果にどの程度影響するか。

## 2. 比べるプロンプト（現状＋キーポイントの異なる3つ）

7月の報告で挙がった疑問（「必須文脈を何として数えているのか」「どうしたら採点ごとのズレをなくせるか」）に対して、
ぶれを抑える方向がまったく違う3つのプロンプトを作り、現状のプロンプトと比べる。全文は `experiments/prompts.py`。

| 条件 | プロンプト | キーポイント | ぶれの原因についての考え方 |
|---|---|---|---|
| `baseline` | 現状 | app.py と同じ。必須文脈と誤りを別々のリストで書かせ、フィードバック文も同時に生成させる | — |
| `a_rubric` | A「定義の明文化」（ルーブリック型） | 観点ごとに「何を1件と数えるか」「何を数えないか」を厳密に書き出す（時制＝述語動詞ごと、名詞＝普通名詞句ごと、構文＝節ごと など）。1つの誤りは1観点だけに記録する | 数える基準があいまいなので、実行ごとに数えるものが変わる |
| `b_clause` | B「手順の固定」（チェックリスト型） | まず発話を節に分け、節ごとに「時制は？一致は？名詞句は？構文は？」の4つの質問に決まった順番で答えさせる | 見る順番や範囲が毎回違うので、拾い漏れが起きる |
| `c_fewshot` | C「採点例の提示」（Few-shot 型） | 規則の説明は最小限にし、採点済みの例を2つ見せる（言い直し・3単現・時制・冠詞・語順の判断を含む） | 規則を文章で説明しても解釈が揺れるので、具体例で見せた方がそろう |

- A・B・C はどれも、seed を固定し、フィードバック文は生成させず、構造化 JSON（スキーマどおりの出力しか返らない形式）で出力させる。
  違いはプロンプトの中身（と B の出力単位）だけ。
- 言い直し・言い淀みを数えない除外ルールは、4つすべてに入っている。
- 件数・エラー率・化石化判定は、どのプロンプトでも Python で計算する。

**補助の分析（余裕があれば）:** 改善のうち、どこまでがプロンプトの中身以外の効果なのかを切り分ける。

| 条件 | 内容 | 分かること |
|---|---|---|
| `seed` | baseline の seed だけ固定 | 乱数の固定だけでどこまで減るか |
| `schema` | A・C と同じ出力形式だが、定義も例もない最小限のプロンプト | 出力形式を変えただけでどこまで減るか（A・C との差が中身の効果） |
| `a_rubric_perq` | プロンプトA を1問ずつ別々に採点して合算 | 一度に処理する量を減らすと、さらに減るか |

## 3. 測る指標

同じ書き起こしを各条件で N 回（基本は5回）採点し、テスター×セット×観点ごとに集計する。

| 指標 | 意味 | 安定していると |
|---|---|---|
| エラー率の SD・幅（最大−最小） | 実行ごとのエラー率の揺れ | 小さい |
| 必須文脈数の SD | 分母（何を数えたか）の揺れ。ぶれの主な原因になっているかを見る | 小さい |
| 全体平均エラー率の SD | セット全体の揺れ | 小さい |
| 化石化判定の一致率 | N 回のうち、同じ判定になった割合 | 100% に近い |
| 判定が割れたセル数 | 化石化あり・なしが実行によって入れ替わった観点の数 | 0 に近い |

注意: **安定していても正しいとは限らない**（毎回同じように間違える可能性がある）。
そこで、研究者本人のデータについて人手で採点し、AI の採点との一致も確認する（妥当性）。
時間がなければ、人手採点は研究者本人の1〜2セット分だけでもよい。

## 4. 手順（スクリプト `experiments/stability.py`）

ローカルの PC（`.streamlit/secrets.toml` がある環境）で実行する。

```bash
# 0) 準備（初回のみ）
pip install -r requirements.txt

# 1) スプレッドシートの書き起こしを CSV に書き出す
python experiments/stability.py export
#    → experiments/transcripts.csv（Excel で開ける）
#      テスター×セットごとの問題数が表示されるので、10問そろっているか確認する

# 2) Whisper の書き起こしで、メインの4条件（baseline, A, B, C）を5回ずつ採点（まず自分のデータだけで試す）
#    研究者本人の Set A〜D は ID「P001」（6月実施）。「KentaH」は6/22の Set A のみ
python experiments/stability.py run --users P001 --runs 5
#    補助の分析も行う場合
python experiments/stability.py run --users P001 --runs 5 --conditions seed,schema,a_rubric_perq

# 3) 集計（条件ごとの比較表が表示され、CSV も出力される）
python experiments/stability.py summarize

# 4) 手動文字起こしを transcripts.csv の manual_transcript 列に入力したら、同じように採点
python experiments/stability.py run --text manual --users P001 --runs 5
python experiments/stability.py summarize

# 5) うまくいったら全テスターに広げる
python experiments/stability.py run --runs 5
```

- **データの内訳（2026-10-07 時点のシート）:** 10問そろっているセットは14セット。
  P001（研究者本人）A〜D、HarunaK A〜D、HaruhiK A・C・D、MakoI A、TaiseiW A、KentaH A（研究者本人の2回目の Set A）。
  HaruhiK B（6問）、MakoI B・C・D（6・1・7問）は欠けているため除外される。
- シートの D 列に「手動チェック」列があると列が1つずれるが、`export` はどちらの並びでも読める。
  GCP の認証がない環境では、スプレッドシートを「ファイル → ダウンロード → CSV」で保存し、`export --from-csv <ファイル>` で読める。
- 結果は `experiments/results/runs.jsonl` に1回ずつ追記される。途中で止めても、もう一度 `run` を実行すれば続きから再開できる。
- `summarize --margin 20` のように指定すると、化石化のしきい値を変えて集計し直せる（API は呼ばない）。
  しきい値の感度分析にも使える。
- `transcripts.csv` と `results/` には参加者の発話が入るので、`.gitignore` で公開リポジトリに上がらないようにしてある。
- 手動文字起こしでは、言い淀み（uh, um）や言い直しも**聞こえたとおりに**書く。
  採点の除外ルール（言い直しは数えない）がきちんと働くかも一緒に確かめられる。

### 費用と時間の目安
- 研究者本人の4セット × メイン4条件 × 5回: API 呼び出しは80回。費用は数ドル程度、時間は同時4並列で15〜20分程度。
- 補助の3条件を足すと、さらに約260回（`a_rubric_perq` は1回の採点で10回呼ぶ）。
- 全テスター（約17セット）に広げると、その4倍程度。費用は実行前に OpenAI の料金ページで確認すること。
