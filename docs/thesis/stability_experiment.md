# 再実験計画: 採点のぶれを抑えるには

作成: 2026-10-06

## 0. 位置づけ

- 先生の指示: 「今のデータで採点すると毎回結果がぶれる。それを安定させるにはどうすればよいかを、何回か再実験して結論とする」
- **研究の中心:** LLM（GPT-4o）による必須文脈の採点の**再現性（信頼性）**と、それを高める方法。
- GPT-4o と Gemini の比較は、余裕があればやる追加研究とする。
- 5月に構想していた「フィードバックでミスが減るかの縦断検証」は**実施しない（確定）**。論文では今後の課題で触れる。

## 1. リサーチクエスチョン（案）

- **RQ1:** 現行の採点方式では、同じ発話データを繰り返し採点したときに、エラー率と化石化の判定がどの程度ぶれるか。
- **RQ2:** プロンプトと出力形式をどう設計すれば、ぶれを抑えられるか。
- **RQ3:** 書き起こしの誤り（Whisper と手動文字起こしの差）は、採点結果にどの程度影響するか。

## 2. ぶれの原因の仮説と、それに対応する条件

7月の報告で挙がった疑問（「必須文脈を何として数えているのか」「一度に送る量が多すぎるのでは」「Role の定義」）を、
そのまま実験の条件にしている。

| 仮説（ぶれの原因） | 対応する条件 | 何を変えるか |
|---|---|---|
| — | `baseline` | 現行の app.py と同じ（temperature=0、10問まとめて1回で採点） |
| サンプリングの乱数 | `seed` | seed を固定する |
| 出力形式があいまい（文脈リストと誤りリストを別々に書かせるので、両者が対応しない。フィードバック文の生成も同時に行っている） | `schema` | 1箇所＝1項目（`is_error` 付き）の構造化 JSON で出力させ、フィードバック文は生成させない |
| 必須文脈の定義があいまい（何を1件と数えるかが実行ごとに変わる） | `rules` | 観点ごとに数える単位を明文化する（時制＝述語動詞ごと、名詞＝普通名詞句ごと、構文＝節ごと など）。1つの誤りは1観点にだけ記録する |
| 一度に処理する量が多すぎて、拾い漏れが起きる | `rules_perq` | 1問ずつ別々に採点して合算する |

条件は左から順に1要素ずつ足していく**段階的な設計**にしている。どの段階でぶれが減ったかで、原因を特定できる。

## 3. 測る指標

同じ書き起こしを各条件で N 回（基本は5回）採点し、テスター×セット×観点ごとに集計する。

| 指標 | 意味 | 安定していると |
|---|---|---|
| エラー率の SD・幅（最大−最小） | 実行ごとのエラー率の揺れ | 小さい |
| 必須文脈数の SD | 分母（何を数えたか）の揺れ。ぶれの主な原因になっているかを見る | 小さい |
| 全体平均エラー率の SD | セット全体の揺れ | 小さい |
| 化石化判定の一致率 | N 回のうち、同じ判定になった割合 | 100% に近い |
| 判定が割れたセル数 | 化石化あり・なしが実行によって入れ替わった観点の数 | 0 に近い |

注意: **安定していても正しいとは限らない**（毎回同じように間違える可能性がある）。
そこで、研究者本人のデータについて人手で採点し、AI の採点との一致も確認する（妥当性）。
時間がなければ、人手採点は研究者本人の1〜2セット分だけでもよい。

## 4. 手順（スクリプト `experiments/stability.py`）

ローカルの PC（`.streamlit/secrets.toml` がある環境）で実行する。

```bash
# 0) 準備（初回のみ）
pip install -r requirements.txt

# 1) スプレッドシートの書き起こしを CSV に書き出す
python experiments/stability.py export
#    → experiments/transcripts.csv（Excel で開ける）
#      テスター×セットごとの問題数が表示されるので、10問そろっているか確認する

# 2) Whisper の書き起こしで、全条件を5回ずつ採点（まず自分のデータだけで試す）
python experiments/stability.py run --users KentaH --runs 5

# 3) 集計（条件ごとの比較表が表示され、CSV も出力される）
python experiments/stability.py summarize

# 4) 手動文字起こしを transcripts.csv の manual_transcript 列に入力したら、同じように採点
python experiments/stability.py run --text manual --users KentaH --runs 5
python experiments/stability.py summarize

# 5) うまくいったら全テスターに広げる
python experiments/stability.py run --runs 5
```

- 結果は `experiments/results/runs.jsonl` に1回ずつ追記される。途中で止めても、もう一度 `run` を実行すれば続きから再開できる。
- `summarize --margin 20` のように指定すると、化石化のしきい値を変えて集計し直せる（API は呼ばない）。
  しきい値の感度分析にも使える。
- `transcripts.csv` と `results/` には参加者の発話が入るので、`.gitignore` で公開リポジトリに上がらないようにしてある。
- 手動文字起こしでは、言い淀み（uh, um）や言い直しも**聞こえたとおりに**書く。
  採点の除外ルール（言い直しは数えない）がきちんと働くかも一緒に確かめられる。

### 費用と時間の目安
- 研究者本人の4セット × 5条件 × 5回: API 呼び出しはおよそ300回（`rules_perq` は1回の採点で10回呼ぶ）。
  費用は数ドル程度、時間は同時4並列で20〜30分程度。
- 全テスター（約17セット）に広げると、その4倍程度。費用は実行前に OpenAI の料金ページで確認すること。

## 5. 明後日（10/8）の発表の構成案

進捗がないぶん、「課題の整理」と「再実験の設計」を示し、予備結果を1つでも出せればよい。

1. **これまでの振り返り（1枚）:** 5名×4セットのデータ取得済み。7月の時点で、同じデータを採点し直すと結果が毎回ずれることが分かっていた。
2. **研究の焦点を定めた（1枚）:** 「採点のぶれを抑えるにはどうするか」を本研究の結論とする。Gemini との比較は追加研究とする。
3. **ぶれの原因の仮説と再実験の設計（1〜2枚）:** §2 の表と §3 の指標。
4. **予備結果（1枚、間に合えば）:** 自分の Set A だけでも `baseline` と `rules` を5回ずつ採点し、SD と化石化一致率を比べる。
   最小構成なら次の1行で10分程度:
   `python experiments/stability.py run --users KentaH --sets "Set A" --conditions baseline,rules --runs 5`
5. **手動文字起こしの状況（1枚）:** 何セット分終わったか。Whisper との差（気づいた例）。
6. **今後のスケジュール（1枚）:** §6。
